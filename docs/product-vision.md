# 小王食堂（Wang's Canteen）产品愿景与范围

> 状态：产品方向定义（2026-10-26）。本文解释“要做成什么”，不是要求一次性实现所有功能。实施具体功能前按阶段任务执行，遵守 AGENTS.md 的当前范围约束。

## 1. 一句话定义

小王食堂是一个基于**家中已有食物库存**，帮助用户**组合一顿饭、决定今天吃什么**，并轻量记录食物消耗的个人生活工具。

目标不是学习烹饪，而是降低每日用餐的决策成本。

## 2. 产品形态与受众

- 第一阶段：独立、移动端优先的 React + TypeScript + Vite Web App，部署到 GitHub Pages。
- 后续方向：可能并入一个包含「大水之王」「下月再说」「小王食堂」的个人生活工具平台，并通过微信小程序访问。**这不是首版开发要求。**
- 主要用户：作者本人，典型场景是下班后从冰箱、冷冻食品和方便食品中决定晚饭。
- 交互：手机单手操作，快捷、简洁、有一点私人食堂的趣味，不应有企业后台或专业营养 App 的复杂度。
- 首版：纯前端、本地优先；使用 localStorage 存储，暂无账户、后端、数据库和云同步。未来存储适配层可替换，但不要预先建设抽象平台。

## 3. 核心用户问题

用户拥有饺子、肉包、炸鸡、汉堡、意面、方便面、米线、粉丝等库存，这些东西早晚都会吃，但：
1. 每天都不知道该选什么；
2. 不希望连续多天重复同一道或同一种食物；
3. 一顿饭往往要**搭配几种食物**，不能假定“有炸鸡”就等于“只吃炸鸡”；
4. 每次用餐的数量和组合不同，需要从剩余库存中扣除；
5. 不希望为了使用工具而维护精细的卡路里、营养或复杂菜谱。

**产品优先解决“今天这一顿怎么吃”，而不是“怎么吃得最健康”。** 除非用户明确设置偏好，否则不要默认基于减脂、营养或热量把推荐固定到某一种食物。

## 4. 核心概念与数据边界

### 食物（Food Item）
家里可用的单项食物或方便食品。最小字段：名称、单位（个/块/份/包等）、当前库存、是否可用；可选分类、备注、默认单次用量。库存允许小数数量（例如半份），数量不能为负。

### 餐食组合（Meal Combination）
由一种或多种食物及其**每餐用量**组成，例如：炸鸡 2 块 + 意面 1 份，肉包 2 个 + 粉丝半份。可以保存常用组合，也能临时自由组合。组合是推荐候选而非固定菜谱；**一个食物可以参与多个组合**。

### 推荐（Recommendation）
推荐对象是一顿可执行的餐食组合，而不只是单品。推荐必须检查各项库存是否足够。近期吃过的组合或单品可降低权重，但不必完全排除。没有足够库存时不推荐无法制作的组合。用户可反复点“换一个”。

### 用餐记录（Meal Record）
保存用餐日期时间、实际吃掉的单品及数量、可选关联组合。确认用餐时扣减库存；取消或编辑记录时应保持库存一致，避免重复扣减。初期可以先支持创建，再逐步支持编辑撤销。

### 库存（Inventory）
允许添加、补货、修正及耗用；库存不足时显示提示。库存记录是工具性数据，不要求条形码、保质期批次或完整采购链路。

## 5. 建议的用户闭环

1. 初次打开：快速添加已有食物及剩余数量（允许手动输入）。
2. 日常打开：首页突出“今天吃什么”，显示一套现有库存可完成的搭配。
3. 不满意：点击“换一个”，获得其他组合；也可以手动更换某一项及用量。
4. 满意：点击“就吃这个/开饭”，确认实际份量。
5. 保存记录、扣减库存；近期推荐开始考虑该记录，下一次不机械重复。
6. 缺货时手动补货，继续使用。

## 6. 功能范围与实施优先级

### MVP（第一版可用闭环）
- 移动端友好的首页与导航；
- 单品库存 CRUD 和补货/修正，持久化到 localStorage；
- 自由搭配多个食物与每项用量，支持保存常用组合；
- 从库存足够的组合中推荐并允许“换一个”；
- 确认用餐、生成历史记录、自动扣减库存；
- 明确的空库存/无可用组合/首次使用引导；
- 页面刷新后数据依然存在；
- 兼容 GitHub Pages 的静态部署。

### 第二阶段（体验优化）
- 近期重复惩罚与随机推荐权重调整；
- 用餐记录编辑/撤销及库存回滚；
- 历史记录查询，最近吃过什么；
- 低库存提醒、采购清单；
- 数据 JSON 导入/导出与本地备份。

### 以后再考虑（不得作为首版前提）
- 微信小程序迁移及统一登录；
- 云端同步、跨设备数据；
- 与「下月再说」联动食材采购支出；
- 菜谱推荐、食材烹饪步骤、保质期管理；
- AI 智能推荐、营养及热量统计；
- 社交、外卖、商城、支付、多租户、角色权限。

## 7. 交互与视觉原则

- 核心首页以“今晚吃什么？”和清晰的组合卡片为中心；
- 优先展示**组合内容、各项用量、是否库存足够、换一个、确认用餐**；
- 两到三步内完成一次用餐记录，避免复杂表单；
- 手机优先，但桌面浏览器应能使用；
- 语言以中文为主，名称保留「小王食堂 / Wang's Canteen」；
- 轻松、有生活气息，避免强制健康建议、评分或负罪感提示；
- 使用普通 UI 组件和 CSS 即可，不为首版引入大型框架。

## 8. 工程约束

- 沿用当前仓库 React、TypeScript、Vite、Node 22、npm。
- GitHub Pages 子路径 /Wangs-Canteen/，不得破坏 Vite base 与已有工作流。
- 初期无后端、密钥或账户；数据默认只保存在当前浏览器设备，卸载/清理站点数据可能丢失。
- 对库存与记录操作需保持一致性；把计算与推荐逻辑从 UI 分离，方便单测。
- 每个开发阶段先定义可验证的验收标准，运行 npm run build。
- 本文属于产品目标，并不覆盖 AGENTS.md 对当前阶段“未经明确要求不开发业务功能”的限制。

## 9. 关键验收场景

1. 库存：炸鸡 8 块、意面 5 份、米线 2 份。定义组合“炸鸡 2 块+意面 1 份”；一次用餐确认后变为炸鸡 6 块、意面 4 份。
2. 若炸鸡仅剩 1 块，不能推荐要求炸鸡 2 块的组合；可提示调整用量。
3. 同一炸鸡既能出现在“炸鸡+意面”，也能出现在“炸鸡+米线”。
4. 今天吃过“炸鸡+意面”，下一次抽取应倾向其他可行组合，仍允许用户主动选择原组合。
5. 刷新页面后库存与用餐历史不丢失。
6. 没有库存或没有可执行组合时，界面应提供清晰的下一步操作，不是空白页。

## 10. 给 Codex 的工作方式

把本文作为**长期产品上下文**，不要一次性实现所有范围。每次只按用户指定的阶段拆解与开发，避免自行引入数据库、AI、微信生态、复杂架构或营养约束。用户对产品选择的优先级为：少纠结、搭配灵活、库存准确、记录省事、避免重复。
